# 재운게임즈 기본 설계 문법

**권위:** 오너 확정 창작 규칙 (2026-10-09). 중앙정책: `company-learning/platform-release-roadmap.json#continuousGameplaySystemEvolutionContract.gameIdentityConceptContract.novelCausalGameGrammar`

## 핵심

**MAIN × A × B × C + @ → 새 게임 정체성 → 실제 플레이**

이 식은 기능 개수의 곱셈이나 분위기 태그의 나열이 아니다. 각 항목을 게임의 실제 입력·행동·상태 변화·스토리 갈등·성장·발견으로 묶는 **인과적 창작 문법**이다.

| 역할 | 기본 의미 | 반드시 적을 것 |
|---|---|---|
| MAIN | 게임의 주제와 정체성. 예: 학교 타이쿤 | 누가 무엇을 하는 어떤 게임인지, 플레이어의 반복 목적 |
| A | 익숙한 게임 시스템 하나 × 그 시스템에 붙는 구체적인 창작 소재 | 시스템 이름, 소재와 출처, 실제 플레이어 선택·규칙·상태 변화 |
| B | A와 구별되는 게임 시스템 하나 × 별도의 창작 소재 | 시스템 이름, 소재와 출처, A의 결과가 B를 바꾸고 B가 A로 돌아오는 인과 |
| C | **창작 주제·소재 두 개를 융합하고, 반드시 메인 장르 하나와 보조 장르 하나를 함께 설계** | 소재 두 가지의 인과 결합 + 메인 장르(중심 경험) + 보조 장르(중심 경험을 변형하는 실제 규칙) |
| @ | 파고들기·발견·숨은 조합·고급 운용·숙련·재해석·재방문 | 발견 조건, 단서, 두 개 이상 시스템/소재와의 연결, 새로운 선택·해결법·결과 |

MAIN은 별도의 “핵심 행동만”을 의미하지 않는다. **게임 정체성·주제**를 먼저 확정하고 핵심 행동을 그 정체성 안에서 도출한다.

A와 B에는 각각 **게임 시스템과 창작 소재가 모두 있어야 한다.** RPG·생존·디펜스·생활·타이쿤·퍼즐·액션·전략·경영·농사·추리·카드·레이싱 등 익숙한 장르와 그 안의 실제 플레이 시스템을 자유롭게 사용한다. A와 B는 별도 기능을 병렬 배치한 것이 아니라 양방향으로 원인·제약·대가·위험·정보·보상·상태를 교환해야 한다. 두 축에 같은 신화나 문명을 붙여도 서로 다른 응용과 실제 인과가 있으면 허용한다.

C는 단순 날씨·버프·이벤트 칸이 아니다. **동서양 역사·인물·종교·철학·미술·음악·건축·문학·무협·과학·괴물·엽기 등 가능한 모든 지식과 문화에서 두 창작 주제/소재를 융합한다.** 이에 더해 **서로 다른 장르 두 개를 반드시 선택한다. 첫 번째는 메인 장르, 두 번째는 보조 장르**다. 예: 메인=호러(위협·불안·위험 판정), 보조=코믹(오해가 판단·괴물 대응·정보 흐름을 바꾸는 실제 규칙), 소재=철학×엽기. 장르 사전은 제한하지 않는다. 메인과 보조 장르는 이름만 다르면 안 된다. 메인 장르는 플레이의 중심 경험·위험·보상을 정의하고 보조 장르는 주요 선택·목표·대응·세계 반응 중 하나 이상을 인과적으로 바꿔야 한다. 두 장르를 서로 바꾸거나 보조 장르를 제거했을 때 플레이가 달라져야 한다.

@는 1개짜리 보너스도, 네 번째 핵심 시스템 축도 아니다. **초기 신규 설계에서는 서로 다른 파고들기 사례 최소 4개를 제시하지만 상한은 없고, 이후 검증된 개발 회차마다 필요한 만큼 끝없이 깊어질 수 있다.** 스탯만 증가시키거나 색깔만 바꾸는 복제물은 제외한다. 숨겨진 방법을 발견할 충분한 단서가 있어야 하며 플레이어가 시도·검증·숙련하는 보상이 새로운 조합·경로·관계·통제·결말·선택이 되어야 한다.

## 예시 — 학교 타이쿤

- MAIN: **학교 타이쿤**. 직접 학교를 짓고 운영해 학생들의 성장과 학교의 위기를 책임지는 게임
- A: **건축 × 로마 신화**. 로마 신전 구조와 제례 배치의 인과가 교실·복도·특수시설의 실제 효과를 바꾼다
- B: **액션 × 로마 신화 속 괴물**. 학교 시설에 축적된 제례 상태 때문에 괴물이 나타나고, 건축·봉인 배치에 따라 액션 공략법이 달라진다. 전투의 결과는 다시 시설 접근·운영·학생 활동에 영향을 준다
- C: **소재=철학 × 엽기 / 메인 장르=미스터리 / 보조 장르=코믹**. 로마 신화의 건축·행동 결과가 금기를 해석할 단서가 되고, 엉뚱한 오해가 괴물 대응·시설 운영·진실 발견 경로를 바꾼다
- @: 비밀 신전 조합, 특정 건물 순서의 봉인, 괴물과 협상하는 공략, 인물 숨은 신분, 과거 지역 재방문, 건설 방식에 따른 다른 학사 운영, 엽기 사건의 철학적 해결책 등 계속 확장
- 결과: **로마 신화 건축·액션에 엽기 철학을 결합한 학교 타이쿤**

## 다섯 가지 필수 창작 강화 규칙

아래 **5개는 새로운 장르나 파이프라인을 추가하는 일이 아니라 MAIN × A × B × C + @ 설계 자체가 통과해야 하는 내용**이다.

1. **의외성 있는 소재 융합**: A와 B가 같은 소재만 반복하지 말고 서로 다른 출처·원리의 소재도 적극 탐색한다. 단순 무작위 조합은 불합격이다. 낯선 둘을 연결하는 **구체적 인과 다리**, 그중 하나를 빼면 사라지는 실제 플레이 효과, 그로 인한 새로운 경험을 작성한다.
2. **스토리 인과 자동 설계**: C의 두 소재와 장르 융합에서 **원인 → 인물의 욕망·갈등 → 플레이어 선택 → 세계/관계 상태 변화 → 다음 사건**이 생성돼야 한다. 완성된 서사 한 문장이 아니라 플레이를 여러 차례 재생할 수 있는 사건 연쇄로 작성한다. 서사가 주도하지 않는 게임도 건물·손님·지역·아이템 등이 왜 반응하는지 인과적 맥락을 연결한다.
3. **A↔B 상호 진화**: A의 선택이 B의 가능 행동·비용·위험을 바꾸고, B의 결과가 A의 다음 선택·구성·운영을 되돌려 바꾼다. 후반에는 두 시스템의 관계 자체가 새로운 숙련 선택으로 변한다. A 단독, B 단독일 때와 비교해 **새로운 플레이가 무엇인지** 증명한다.
4. **C 메인·보조 장르 융합**: 두 창작 소재와 **메인 장르 1개 + 보조 장르 1개**를 결합한다. 두 장르는 독립된 실제 플레이 효과를 갖고 서로 다르다. 보조 장르가 단순 말투·색깔·외형이면 불합격이다. **보조 장르 제거 시험**에서 행동·위험·정보·목표가 달라져야 한다.
5. **@ 제한 없는 깊이**: 초기에는 숨겨진 발견·고급 조합 최소 4개를 구체적으로 설계하되 영구 개수 제한을 두지 않는다. 단서 → 실험 → 숙련 → 새로운 선택 → 더 깊은 의문·재방문으로 이어진다. 검증된 다음 개발 회차마다 게임의 기존 시스템과 소재를 더 깊게 연결한다. 무조건 콘텐츠만 쌓지 않는다.

**완료 기준:** 설계 필드에 값이 있다는 사실만으로 통과시키지 않는다. 실제 플레이 진입, 상태 입출력, 실패·복구, 플레이 중 보이는 차이, 소스 책임 위치와 독립 검증까지 연결해야 한다. 이야기나 장르 설명만 늘려서 점수를 얻지 않는다.

## 설계 심사와 실제 구현

1. MAIN의 게임 주제를 확인하고, A와 B 각각에서 **시스템 + 소재**의 존재를 검사한다.
2. A→B→A의 **구체적인 상태·행동·반응**이 플레이 흐름에 있는지 확인한다.
3. C의 창작 소재 두 개가 인과적으로 연결돼야 한다. **장르는 서로 다른 메인 하나와 보조 하나를 반드시 요구**하고 보조 장르가 실제 플레이 선택·위험·정보·결과를 바꾸는지 검사한다. 보조 장르를 빼도 똑같이 플레이된다면 실패다.
4. A/B/C를 하나라도 제거하면 플레이 구조나 서사 결과가 바뀌는지 비교한다. 없으면 재설계한다.
5. @에 발견 조건과 플레이 결과를 연결한다. 초기 4개는 최소 증거일 뿐 상한이 아니다.
6. 1분·5분·15분·30분, 중후반·재방문 시점에 **행동·규칙·목표·조합의 깊이**가 실제로 달라지는지 시뮬레이션한다.
7. 설계 완료 점수와 게임 플레이 완료를 혼동하지 않는다. 구현은 기존 게임 책임 함수·데이터 구조에서 진행하고 실제 소스 변경과 독립 런타임 QA로 검증한다.

## 기존 게임 설계의 전면 재작성

기존 게임은 이름이나 현재 정상 실행 중인 코드만 기준선으로 삼는다. **MAIN 또는 일부 핵심 소재만 적힌 이전 설계안을 “보존해야 할 설계”로 승계하지 않는다.** 설계마다 A·B의 **개별 소재**, C의 **두 창작 소재와 메인·보조 장르 2개**, 인과관계, 실제 플레이, 제한 없는 @ 성장층을 새로 작성·심사한다. 새 설계가 검증되기 전에는 완료·PASS나 기존 설계의 충족을 주장하지 않는다.

작동 중인 게임 소스·기존 저장 데이터·밸런스·보상·멀티 서버 권한은 기존 구조대로 유지한다. 새로운 설계가 곧바로 실행 게임 변경 허가를 뜻하지 않는다. 기존 정식 디자인·개발·QA·배포 흐름을 이용하며 별도 큐·래퍼·우회 파이프라인을 만들지 않는다.
