# 재운게임즈 기본 설계 문법

**권위:** 오너 확정 창작 규칙 (2026-10-09). 중앙정책: `company-learning/platform-release-roadmap.json#continuousGameplaySystemEvolutionContract.gameIdentityConceptContract.novelCausalGameGrammar`

## 핵심

**MAIN × A × B × C + @ → 새 게임 정체성 → 실제 플레이**

이 식은 기능 개수의 곱셈이나 분위기 태그의 나열이 아니다. 각 항목을 게임의 실제 입력·행동·상태 변화·스토리 갈등·성장·발견으로 묶는 **인과적 창작 문법**이다.

| 역할 | 기본 의미 | 반드시 적을 것 |
|---|---|---|
| MAIN | 게임의 주제와 정체성. 예: 학교 타이쿤 | 누가 무엇을 하는 어떤 게임인지, 플레이어의 반복 목적 |
| A | 익숙한 게임 시스템 하나 × 그 시스템에 붙는 구체적인 창작 소재 | 시스템 이름, 소재와 출처, 실제 플레이어 선택·규칙·상태 변화 |
| B | A와 구별되는 게임 시스템 하나 × 별도의 창작 소재 | 시스템 이름, 소재와 출처, A의 결과가 B를 바꾸고 B가 A로 돌아오는 인과 |
| C | **광범위한 창작 주제·장르·소재 중 정확히 두 개를 융합. 적어도 하나는 반드시 장르** | 두 이름, 각각의 종류(장르/창작 소재), 충돌·융합이 실제 플레이·서사·세계 규칙에 주는 변화 |
| @ | 파고들기·발견·숨은 조합·고급 운용·숙련·재해석·재방문 | 발견 조건, 단서, 두 개 이상 시스템/소재와의 연결, 새로운 선택·해결법·결과 |

MAIN은 별도의 “핵심 행동만”을 의미하지 않는다. **게임 정체성·주제**를 먼저 확정하고 핵심 행동을 그 정체성 안에서 도출한다.

A와 B에는 각각 **게임 시스템과 창작 소재가 모두 있어야 한다.** RPG·생존·디펜스·생활·타이쿤·퍼즐·액션·전략·경영·농사·추리·카드·레이싱 등 익숙한 장르와 그 안의 실제 플레이 시스템을 자유롭게 사용한다. A와 B는 별도 기능을 병렬 배치한 것이 아니라 양방향으로 원인·제약·대가·위험·정보·보상·상태를 교환해야 한다. 두 축에 같은 신화나 문명을 붙여도 서로 다른 응용과 실제 인과가 있으면 허용한다.

C는 날씨·버프·이벤트 같은 단순 보조 시스템 칸이 아니다. 동양·서양 역사, 인물, 회화, 음악, 건축, 문학, 종교, 신화, 철학, 과학, 기술, 생물, 무협, 선협, 정치, 사회, 코믹, 엽기, 괴물, 미스터리, 호러, 일상 등 **열거할 수 없는 전체 창작 소재 영역**을 활용한다. 단, 그중 결합할 두 소재의 **최소 한 가지는 게임의 장르·서사 장르**로 명시해야 한다. 호러·코믹·엽기·미스터리·무협·판타지·스릴러 등은 장르 후보일 수 있다. 미리 정한 제한된 단어 사전에서만 선택하도록 강제하지 않는다. C는 분위기 라벨에 그치지 않고 A/B·캐릭터·사건·세계의 실제 규칙을 바꾼다.

@는 1개짜리 보너스도, 네 번째 핵심 시스템 축도 아니다. **초기 신규 설계에서는 서로 다른 파고들기 사례 최소 4개를 제시하지만 상한은 없고, 이후 검증된 개발 회차마다 필요한 만큼 끝없이 깊어질 수 있다.** 스탯만 증가시키거나 색깔만 바꾸는 복제물은 제외한다. 숨겨진 방법을 발견할 충분한 단서가 있어야 하며 플레이어가 시도·검증·숙련하는 보상이 새로운 조합·경로·관계·통제·결말·선택이 되어야 한다.

## 예시 — 학교 타이쿤

- MAIN: **학교 타이쿤**. 직접 학교를 짓고 운영해 학생들의 성장과 학교의 위기를 책임지는 게임
- A: **건축 × 로마 신화**. 로마 신전 구조와 제례 배치의 인과가 교실·복도·특수시설의 실제 효과를 바꾼다
- B: **액션 × 로마 신화 속 괴물**. 학교 시설에 축적된 제례 상태 때문에 괴물이 나타나고, 건축·봉인 배치에 따라 액션 공략법이 달라진다. 전투의 결과는 다시 시설 접근·운영·학생 활동에 영향을 준다
- C: **엽기(장르) × 철학(소재)**. 신들의 이상한 규율이 학생들의 자유·판단·윤리 갈등을 만들어 실제 선택과 사건 분기로 이어진다
- @: 비밀 신전 조합, 특정 건물 순서의 봉인, 괴물과 협상하는 공략, 인물 숨은 신분, 과거 지역 재방문, 건설 방식에 따른 다른 학사 운영, 엽기 사건의 철학적 해결책 등 계속 확장
- 결과: **로마 신화 건축·액션에 엽기 철학을 결합한 학교 타이쿤**

## 설계 심사와 실제 구현

1. MAIN의 게임 주제를 확인하고, A와 B 각각에서 **시스템 + 소재**의 존재를 검사한다.
2. A→B→A의 **구체적인 상태·행동·반응**이 플레이 흐름에 있는지 확인한다.
3. C에 주제 2개가 있고 **장르가 최소 1개**인지 검사한다. 이름만 붙인 장르·태그를 통과시키지 않는다.
4. A/B/C를 하나라도 제거하면 플레이 구조나 서사 결과가 바뀌는지 비교한다. 없으면 재설계한다.
5. @에 발견 조건과 플레이 결과를 연결한다. 초기 4개는 최소 증거일 뿐 상한이 아니다.
6. 1분·5분·15분·30분, 중후반·재방문 시점에 **행동·규칙·목표·조합의 깊이**가 실제로 달라지는지 시뮬레이션한다.
7. 설계 완료 점수와 게임 플레이 완료를 혼동하지 않는다. 구현은 기존 게임 책임 함수·데이터 구조에서 진행하고 실제 소스 변경과 독립 런타임 QA로 검증한다.

## 기존 게임 설계의 전면 재작성

기존 게임은 이름이나 현재 정상 실행 중인 코드만 기준선으로 삼는다. **MAIN 또는 일부 핵심 소재만 적힌 이전 설계안을 “보존해야 할 설계”로 승계하지 않는다.** 설계마다 A·B의 **개별 소재**, C의 **장르 포함 두 소재**, 인과관계, 실제 플레이, 제한 없는 @ 성장층을 새로 작성·심사한다. 새 설계가 검증되기 전에는 완료·PASS나 기존 설계의 충족을 주장하지 않는다.

작동 중인 게임 소스·기존 저장 데이터·밸런스·보상·멀티 서버 권한은 기존 구조대로 유지한다. 새로운 설계가 곧바로 실행 게임 변경 허가를 뜻하지 않는다. 기존 정식 디자인·개발·QA·배포 흐름을 이용하며 별도 큐·래퍼·우회 파이프라인을 만들지 않는다.
