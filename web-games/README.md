# 일반 웹게임

## 원본과 엔진

- 일반 웹게임의 원본은 `web-games/<game-id>/`에 두고 기존 HTML·JavaScript·게임 로직·저장 키를 유지한다.
- 새 일반 웹 3D 게임은 기존 Vibe2/Vibe3 코딩 워커에서 PlayCanvas(웹지엘2 우선)를 기본 선택한다. 물리 요구가 높은 게임은 바빌론을 검토한다.
- 쓰리·바빌론·플레이캔버스·기존 웹지엘을 사용하는 게임은 검증 없이 엔진을 교체하거나 렌더러를 중복 추가하지 않는다.
- 등록된 3D 자산과 라이선스를 우선 재사용하고 필요한 지오메트리·애니메이션·충돌·장면을 기존 책임 코드에 적용한다.

## 전 화면 네이티브 3D 강제 정책 — 2026-10-18

- **월드·HUD·인벤토리·도움창·상점·제작·지도·설정·데미지 숫자·아이콘·알림 등 플레이어가 보는 모든 화면 구성요소는 실재 3D 지오메트리로 렌더링한다. 2D 표현 예외는 없다.**
- 기존 게임 렌더러(PlayCanvas/Three/Babylon/WebGL)의 3D 씬 안에서 실제 메시·두께·법선·재질·조명·원근/깊이 테스트를 사용한다. 화면에 고정된 정보창도 **카메라 공간의 3D 메시 모델**로 배치한다.
- 모든 표시용 글자는 실제 3D 문자 메시·검증된 글리프 지오메트리를 사용한다. DOM/CSS/HTML 카드·HUD, Canvas 2D·스프라이트 글자, CSS transform/perspective 기반 가짜 3D, 평면 UI 텍스처, 2D 렌더 타겟은 3D UI로 인정하지 않는다. WebGL 캔버스는 3D 씬의 최종 래스터 출력 대상으로만 허용한다.
- 메뉴·버튼·툴팁은 실제 공간 메시와 레이캐스트/포인터 입력을 연결한다. 시야·터치 영역·텍스트 가독성·입력 가능 상태도 실제 3D 카메라 관찰 결과로 확인한다.
- **2D 화면은 임시 개발용이라도 3D 검증 통과로 인정하지 않는다.** 기존 플레이 가능 소스는 3D 대체본과 기능/저장/성능/실행 검증이 끝날 때까지 보존하되, 2D UI가 남아 있으면 최종 3D QA는 실패로 둔다.
- 중앙 기준: `company-learning/platform-release-roadmap.json#livingMotionVisualQualityContract.minimumSpatialPresentation`. 별도 엔진·우회 경로·평가 점수만의 승인 금지.

## 3D 최종 기준

- 실제 삼각형 메시, 깊이 테스트가 적용된 렌더링, 3D 카메라, 공간·충돌·입력 결과가 필수다.
- 평면 캔버스·DOM 카드·아이소메트릭·시차 연출·2.5D·표시용 속성만으로는 통과할 수 없다.
- 기존 2D 게임은 원래 규칙·저장·진행·밸런스를 유지한 채 현재 파일 안에서 3D로 전환한다. 실제 3D 대체본을 검증하기 전에는 기존 플레이 가능한 소스를 제거하지 않는다.
- 모바일 터치·화면 회전·성능·메모리·실제 브라우저 시작·렌더·재시작·저장 복원을 기존 브라우저 검사와 독립 검수·회귀 단계에서 확인한다.
- 런타임·독립 QA 증거가 없으면 최종 3D 통과나 배포 성공으로 표시하지 않는다.

## 별도 보류 플랫폼

- `unity-games/<game-id>/`는 별개의 기존 Unity 원본이며, Unity 웹/앱 개발의 OWNER_HOLD를 유지한다.
- 일반 웹게임 개발 재개로 Unity 웹 원본을 덮어쓰거나 Unity 웹의 자동 개발·배포를 허용하지 않는다.

## 개발 절차

중앙정책은 `company-learning/platform-release-roadmap.json`을 기준으로 한다. 설계 문법 `MAIN = A + B + C + D + @`를 사용하고, 기존 BUILD_UP·F0~F9·소스 워커·브라우저 검증만 활용한다. 새 파이프라인·우회용 워크플로·임의의 밸런스/세이브 변경은 금지한다.
